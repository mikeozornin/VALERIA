# MCP Memory Server для CLine

Сервер памяти для агента CLine, предоставляющий инструменты для работы с единой памятью и тегами.

## Структура базы данных

```
tags (Теги)
├── id (INTEGER PRIMARY KEY)
├── name (TEXT UNIQUE)
└── created_at (TIMESTAMP)

notes (Заметки)
├── id (INTEGER PRIMARY KEY)
├── content (TEXT)
├── created_at (TIMESTAMP)
├── updated_at (TIMESTAMP)
├── version (INTEGER)
├── status (active | superseded)
├── superseded_by_note_id (FK → notes)
└── superseded_at (TIMESTAMP)

note_tags (Связь заметок и тегов)
├── note_id (INTEGER FK → notes)
├── tag_id (INTEGER FK → tags)
└── PRIMARY KEY (note_id, tag_id)

note_versions (Неизменяемая история версий)
├── note_id, version
├── content, tags_json, status
└── change_type, created_at

notes_fts (FTS5-индекс текста и тегов)
```

## Установка

1. Активируйте виртуальное окружение и установите зависимости:
```bash
cd mcp-memory-server
source venv/bin/activate
pip install -r requirements.txt
```

2. База данных будет создана автоматически в `~/.mcp-memory/memory.db`

Сервер использует схему 3 без проектов. Новая пустая БД создаётся автоматически.
Существующая схема 2 требует явной миграции; другие версии отклоняются.

## Переход со схемы 2

1. Остановите все процессы Memory MCP, использующие эту БД, в подключённых клиентах.
2. Выполните из каталога сервера:

```bash
venv/bin/python migrate.py --database /home/appuser/.mcp-memory/memory.db
```

Путь можно заменить на значение вашего `MCP_MEMORY_DB_PATH`. Команда создаёт рядом
резервную копию через SQLite backup API с правами `0600` и выводит её путь.
Опция `--backup /path/to/new-backup.db` задаёт другой путь; существующий файл
никогда не перезаписывается. Миграция выполняется транзакционно; при ошибке
исходная схема и данные сохраняются. Повторный запуск на схеме 3 ничего не меняет.

Сохраняются ID, содержимое, временные метки, прежняя история и ссылки замещения.
Прежний проект становится обычным тегом `legacy-project:имя`. Каждая заметка
получает новую версию с этим тегом и `change_type=migrated_to_unified_memory`;
`updated_at` сохраняется, чтобы не менять порядок свежести при миграции.
Восстановление старой версии возвращает её точные прежние теги, поэтому может
убрать миграционный тег. Источник по-прежнему доступен в истории миграции.

3. Перезапустите или переподключите Memory MCP в клиентах для обновления инструментов.

Это несовместимое изменение API: `project_name`, поля `project_id`/`project_name`
и инструменты `get_project_list`/`create_project` удалены. Обновите клиентские
промпты (основной промпт: `../promt`). Версионирование и операции по ID сохранены.
Для отката остановите все серверы, сохраните текущую БД, восстановите резервную
копию через SQLite backup API и верните код схемы 2 перед перезапуском.


## Настройка в CLine

Добавьте следующую конфигурацию в настройки CLine:

```json
{
  "mcpServers": {
    "memory": {
      "command": "/home/appuser/mcp/mcp-memory-server/venv/bin/python",
      "args": ["/home/appuser/mcp/mcp-memory-server/server.py"],
      "cwd": "/home/appuser/mcp/mcp-memory-server"
    }
  }
}
```

Или через файл конфигурации MCP:

```json
{
  "mcpServers": {

      "command": "/home/appuser/mcp/mcp-memory-server/venv/bin/python",

      }
```

## Доступные методы

### `get_context(query=None, tags=None, match_all_tags=True, limit=5, include_superseded=False)`

Искать по всей памяти. По умолчанию — FTS5 (`unicode61`) / BM25, слова через ИЛИ.
При `MCP_MEMORY_HYBRID=true` дополнительно выполняется семантический поиск
Qwen3-Embedding-4B и объединение через RRF с приоритетом точных идентификаторов.
При недоступности embeddings используется BM25. Морфологическое расширение
лексической ветки не выполняется.
Без `query` возвращаются последние изменённые заметки с устойчивым порядком по ID.

- `tags=None` или `[]`: без ограничения тегами.
- `match_all_tags=True`: нужны все переданные теги; `False`: любой из них.
- Теги сопоставляются точно, фильтры применяются до ранжирования и `limit`.
- `limit`: от 1 до 100. По умолчанию устаревшие заметки скрыты.
- Результат: список заметок с `relevance_score` (`None` без текстового запроса).

### `get_notes_by_tags(tags, match_all_tags=True, page=1, limit=5, include_superseded=False)`

Поиск по точным тегам по всей памяти. Режимы совпадения такие же, как в
`get_context`. Повторяющиеся теги не меняют результат. Пустые `tags` дают пустую
выборку. `page >= 1`, `limit` от 1 до 100.

Результат: `notes`, `total`, `page`, `total_pages`. По умолчанию устаревшие заметки
скрыты. Для категорий «architecture ИЛИ decisions» передавайте `match_all_tags=False`.
Для «codestyle И component:example-backend» оставьте `True`.

### `add_note(content, tags)`

Добавить самостоятельную заметку. `content` — непустой Markdown с заголовком и
областью применения, `tags` — список тегов (может быть пустым, максимум 50).
Одна заметка может относиться к нескольким компонентам. Общие знания не требуют
тега компонента. Проверяйте область применения решения перед использованием.

Заметка содержит `id`, `content`, `tags`, `created_at`, `updated_at`, `version`,
`status`, `superseded_by_note_id`, `superseded_at`.

### `get_all_tags()`
Получить список всех тегов.

**Возвращает:** `list[dict]` - Список тегов

---

### `get_note_by_id(note_id: int)`
Получить заметку по ID.

**Параметры:**
- `note_id` (int): ID заметки

**Возвращает:** `dict | None` - Заметка или None

---

### `update_note(note_id: int, expected_version: int, content: str | None = None, tags: list[str] | None = None)`
Обновить заметку и создать новую версию. `expected_version` защищает от потери параллельных изменений. При несовпадении версии возвращает `status="conflict"` и `current_note`, ничего не записывая.

### `resolve_note_conflict(note_id: int, expected_current_version: int, merged_content: str, merged_tags: list[str])`
Сохранить ручную объединенную версию. Если заметка снова изменилась, операция также вернёт конфликт.

### `get_note_history(note_id: int, limit: int = 20)`
Получить неизменяемую историю версий.

### `restore_note_version(note_id: int, version: int, expected_version: int)`
Восстановить снимок как новую версию, не стирая историю.

### `mark_note_superseded(note_id: int, replacement_note_id: int, expected_version: int)`
Пометить устаревшее решение и связать его с любой активной замещающей заметкой.

---

### `delete_note(note_id: int)`
Удалить заметку по ID.

**Параметры:**
- `note_id` (int): ID заметки

**Возвращает:** `bool` - Успешность удаления

---

## Примеры использования

### Добавить заметку
```
add_note(content="## Решение о сборке\nОбласть: example-backend и example-worker", tags=["architecture", "conan", "component:example-backend", "component:example-worker"])
```

### Найти релевантный контекст
```
get_context(query="миграция PostgreSQL", tags=["architecture"], limit=5)
```

### Обновить заметку без потери параллельных изменений
```
update_note(note_id=42, expected_version=3, content="Обновлённое решение")
```

### Найти заметки по тегам с пагинацией
```
get_notes_by_tags(tags=["codestyle", "component:example-backend"], page=1, limit=5)
```

## Проверка

```bash
venv/bin/python -m unittest discover -s tests -v
```

Тесты используют временные базы: общий поиск и комбинации тегов, пагинацию,
конфликты конкурентных записей, историю/восстановление/устаревание, миграцию
схемы 2 с резервной копией, сохранением данных и откатом при ошибке.

## Гибридный поиск и индекс эмбеддингов

Публичные имена инструментов, аргументы и структура ответа сохранены. При текстовом
запросе `relevance_score` означает RRF с бонусом за явные идентификаторы, при откате
на BM25 — `-bm25`, без запроса — `None`. Численные пороги между режимами непереносимы;
score не является вероятностью. Режим и причину отката сервер пишет в stderr.

Алгоритм:

1. Один документ на заметку: содержимое (включая Markdown-заголовок) и отсортированные
   теги. Документы отправляются без префикса; запрос — с английской инструкцией
   `Instruct: ...\nQuery: ...`.
2. Токенизатор Qwen проверяет длину до отправки, без truncation (лимит 32000 минус
   резерв 16 токенов). Слишком длинный документ остаётся в очереди и доступен через
   BM25; остальные документы батча продолжают индексироваться.
3. Нормализованные float32-векторы хранятся в SQLite. Поиск точный, по всем
   подходящим актуальным векторам; отдельный сервис векторной БД не требуется.
4. Фильтры тегов и статуса применяются до top-k в обеих ветках. По умолчанию берём
   по 30 кандидатов; если `limit` больше, расширяем пул до `limit`.
5. Объединение по ID: сумма `1/(60+rank)` с равными весами. Полное совпадение явно
   указанного идентификатора вида `PROJ-123` добавляет 1 за каждый уникальный ID;
   такие совпадения включаются даже вне top-30. Это сохраняет точный поиск задач,
   который ухудшался при обычном RRF. Поиск идентификаторов нечувствителен к регистру
   и не сопоставляет `PROJ-12` с `PROJ-123`.
6. Сортировка по итоговой оценке, затем `updated_at DESC, id DESC`; до `limit`
   уникальных заметок. Общего порога полезности нет: отсутствие подходящих знаний
   не гарантирует пустую выдачу.

Индекс — добавочное, восстанавливаемое расширение схемы заметок v3:
`embedding_sources` хранит текст/хеш и сроки повторов, `note_embeddings` — вектор,
хеш, модель, размерность и профиль (endpoint/model/dimensions/формат документа).
При запуске источники сверяются с заметками. Текст, версии, история и даты заметок
при индексации не изменяются.

Изменение текста/тегов и восстановление версии атомарно обновляют источник в
той же транзакции, что и заметку. Старый вектор с другим хешем сразу исключается из
поиска. Фоновый поток MCP опрашивает очередь с интервалом до 5 секунд, отправляет
батчи вне транзакции и сохраняет ответ только при совпадении хеша. Неизменившийся
документ не пересчитывается. При ошибке изменение заметки сохраняется, очередь
переживает рестарт; интервалы повторов растут до 300 секунд. Удаление заметки
каскадно удаляет её индекс. Фильтрация superseded не зависит от готовности вектора.

### Настройка

| Переменная | По умолчанию |
| --- | --- |
| `MCP_MEMORY_HYBRID` | `false` |
| `MCP_MEMORY_EMBEDDING_BASE_URL` | `http://127.0.0.1:8080/v1` |
| `MCP_MEMORY_EMBEDDING_API_KEY` | пусто |
| `MCP_MEMORY_EMBEDDING_MODEL` | `Qwen/Qwen3-Embedding-4B` |
| `MCP_MEMORY_EMBEDDING_DIMENSIONS` | `2560` |
| `MCP_MEMORY_EMBEDDING_TIMEOUT` | `30` секунд на весь HTTP-вызов с повторами |
| `MCP_MEMORY_EMBEDDING_BATCH_SIZE` | `8` |
| `MCP_MEMORY_CANDIDATES` | `30` |
| `MCP_MEMORY_TOKENIZER_PATH` | требуется путь к tokenizer.json при включении |

При 2560 клиент не передаёт `dimensions`: текущий шлюз отклоняет явное 2560, но
возвращает 2560 по умолчанию. Для уменьшения размерности параметр передаётся;
на проверенном сервисе допустимы 512/1024/2048. Размерность ответа всегда проверяется.
Смена модели/endpoint/размерности исключает старые векторы и ставит документы на
переиндексацию. При замене модели за тем же именем переиндексируйте производную
таблицу явно; автоматическое обнаружение замены весов API не предоставляет.

Подготовка из каталога сервера (секреты передавайте через окружение клиента MCP):

```bash
venv/bin/python -m pip install -r requirements.txt
venv/bin/python download_tokenizer.py /path/to/qwen3-tokenizer.json
export MCP_MEMORY_TOKENIZER_PATH=/path/to/qwen3-tokenizer.json
export MCP_MEMORY_DB_PATH=/path/to/memory.db
export MCP_MEMORY_EMBEDDING_BASE_URL=http://127.0.0.1:8080/v1
venv/bin/python index_memory.py
venv/bin/python index_memory.py --status
```

`index_memory.py` перед изменениями делает SQLite backup с правами 0600. Готовые
векторы пропускаются. Для немедленного повтора отложенных ошибок — `--retry-now`.
После индексации задайте `MCP_MEMORY_HYBRID=true` в окружении MCP и переподключите
клиент. Для отката поиска достаточно `false`; производный индекс можно сохранить.
Работающие процессы старой версии необходимо переподключить: они не ставят новые
изменения в очередь. При частично готовом индексе BM25 продолжает видеть все заметки.

### Воспроизводимая проверка

```bash
venv/bin/python -m unittest discover -s tests -v
venv/bin/python evaluate_search.py --queries eval/queries.json --output /tmp/memory-eval.json
venv/bin/python evaluate_search.py --queries eval/holdout.json --output /tmp/memory-holdout.json
```

Оценка выполняется на отдельном SQLite-снимке. Запросы размечены вручную до просмотра
соответствующей выдачи. Hit@5 — наличие хотя бы одной ожидаемой заметки в пятёрке;
MRR@5 — обратная позиция первой ожидаемой заметки, либо 0. Списки ожидаемых ID не
исчерпывают все релевантные заметки, поэтому эти показатели не являются полной
оценкой recall/NDCG. Это локальная проверка на небольшом наборе, не независимый
пользовательский бенчмарк. Время включает API; vector/hybrid используют один и тот
же embedding запроса. Исходный результат RRF сохранён отдельно от исправленного.

### Оценка качества поиска

Для собственной проверки подготовьте обезличенный SQLite-снимок и отдельные наборы
запросов для разработки и контрольной оценки. Сравнивайте BM25, векторный и гибридный
режимы по Hit@5 и MRR@5, фиксируя параметры модели, размерность, число кандидатов и
RRF k. Не публикуйте снимок, тексты заметок и результаты, полученные на закрытых
пользовательских данных.

Точные идентификаторы получают общий приоритет без списка специальных номеров задач.
Если embedding API недоступен или отвечает с ошибкой, штатный поиск возвращается к
BM25. Полученные на небольшой ручной выборке показатели нельзя переносить на все
пользовательские запросы.

Проверки реализации: 33 теста, включая настоящий stdio MCP с HTTP-фикстурой,
обновление/восстановление и фоновую индексацию; отдельный smoke-тест локального
stdio MCP с реальным API. Для повторения обеих оценок на одном снимке используйте
`evaluate_search.py --database /path/to/snapshot.db` с соответствующим `--queries`.
